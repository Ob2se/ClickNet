# Clicknet standalone Box3D server

Replication now uses up to three persistent worker threads plus the main thread.
Use `--replication-workers 0` for a sequential comparison. See
[MULTITHREADING.md](MULTITHREADING.md) for changes and load-test measurements.

Build `clicknetserver.sln` as **x64 Debug** or **x64 Release** in Visual Studio 2022. The project compiles the shared Box3D loader and mover from `../Plugins/Box3D/Source/ThirdParty/ClickNetShared` and links the Box3D and GameNetworkingSockets libraries in this checkout. The server, load test, and Unreal client all include the same `ClickNetWire.h`; rebuild all three after changing it.

Export the current Unreal level to `../Saved/Box3DTest.box3d`, then run, for example:

You can also double-click `StartRelease.cmd` in the server project folder. It launches the Release build and keeps the console open if startup fails. With no `--map`, the server searches the working directory and executable ancestors for `Saved/Box3DTest.box3d`.

```powershell
.\x64\Release\clicknetserver.exe --map ..\Saved\Box3DTest.box3d --spawn 0 0 2
```

`--spawn x y z` is optional and uses **Box3D meters**, with a default of `0 0 2`. Set it to the desired player start for the map. `--interest-radius meters` controls replication range (default 40 m; allowed 5–500 m). The server listens on UDP port **27015** and targets **60 fixed physics steps per second**, catching up by up to three steps when a loop runs late. Stop it with **Ctrl+C**. The server and Unreal client must load the same exported `.box3d` file; the Welcome packet carries its hash so the client can reject a mismatch. Re-export and restart the server after changing level collision.

The server receives world-space movement and jump input and simulates one capsule mover per connection at 60 Hz. The client sends an input command when movement or yaw changes, on jump, and once per second as a refresh. The server holds that command between packets and stops movement after three seconds without a refresh. The owner receives authoritative position, velocity, grounded state, and input acknowledgement on prediction error or at least every 500 ms. Other players and dynamic bodies are replicated only within the interest radius. A 20 m spatial grid avoids scanning every player/body pair across a large map. Remote visibility scans are distributed over 18 ticks (about 3.3 Hz per recipient), while owner prediction checks still run every tick and changed remote movement states enter the budgeted update path without waiting for a scan. Remote state is also sent on prediction error or a five-second baseline; a removal event clears remote players that leave visibility. Body states include orientation and angular velocity, and the server predicts both translation and rotation before deciding whether another packet is needed. Bodies within 3 m of a player receive 10 Hz corrections during contact. The client advances its local physics between updates and corrects drift. Static geometry is supplied by the shared `.box3d` map.

The wire protocol is version 6. Rebuild and restart the server, Unreal client, and load-test bots together; version 5 processes cannot exchange packets with version 6. Movement uses unreliable, unordered, no-Nagle packets with up to 16 sequenced commands (341 bytes maximum). The sender retains up to 64 outstanding commands, sends changes immediately, and retries unacknowledged history every 50 ms. Each packet carries the newest command plus the oldest missing commands. Owner snapshots include a 64-bit selective receipt acknowledgement; changed receipts trigger an owner snapshot after at most the existing three-tick send gate, subject to server loop timing. Remote batches remain 45 bytes per player, without the extra owner acknowledgements. The client defers corrections covering any command still unacknowledged, including holes below the newest receipt.

Recovered commands retain their original simulation ticks and are deduplicated by sequence, so retransmission cannot repeat a jump. Within the 32-step replay window, a recovered jump reconstructs the appropriate step. Outside that window, an old movement command cannot override newer received movement; a recovered jump is offered on the next step using current held movement (normal grounded checks still apply). Recovery is bounded: after 64 newer commands an unreceived command can expire, including a jump. The bot console and CSV report `expiredCommands`/`expired_commands`; this should stay zero in healthy runs. This scheme removes reliable-stream ordering delays but does not guarantee delivery through an unlimited outage. Retry traffic increases while acknowledgements are missing.

Movement commands are applied on their client input ticks. The acknowledgement advances only when that step is simulated. The server retains 32 mover steps and reconstructs them when a recent command arrives late, preserving intermediate turns and one-step jump events. This replays the mover against current world collision; it does not rewind dynamic bodies or repeat world simulation. A newer command older than the retained window is applied on the next step; superseded movement is discarded, with the bounded jump recovery described above. The JSON diagnostics include cumulative `lateInputCommands` and `inputHistoryMisses`, and `inputReplaySteps` from the last loop. Bots rebase their command counter from owner acknowledgements when their own receive loop runs late.

Bandwidth depends on nearby entity density, motion, and error thresholds. The 40 m default supports large distributed maps; thousands of players concentrated inside each other's interest radius still produce quadratic visibility traffic. Server capacity also depends on Box3D simulation cost and host/network hardware, and must be measured with a load test before claiming a connection count.

Remote motion changes use a per-recipient cursor in a bounded change log. A recipient deferred by the replication budget retains pending turns, jumps, and landings until its next successful send; repeated changes are coalesced to the latest player state. Notifications occur when a queued input becomes active, or when replay changes the mover, rather than when a future input merely arrives. Owner states are sent first. Remote work uses the time remaining before a 14 ms loop target, and recipients rotate fairly. This adds no fixed client display buffer. If a recipient falls behind the retained change log, a full visibility scan restores its state.

The C++ headless generator in `LoadTest` uses the real GameNetworkingSockets connection and ClickNet wire format. Its README gives ramped idle, spread, cluster, and target test commands. Run the server and generator separately; the generator never starts the server.

Each replication pass also checks each player's actual motion against the trajectory at its last motion notification. Position error over 12 cm or velocity error over 0.4 m/s creates a change-log event, including collision stops, wall releases, slope changes, and input-timeout stops. These error-triggered events are spaced at least three physics ticks apart; existing input and grounded transitions can notify sooner. Predictable straight travel and jump gravity do not generate these extra events. Recipient delivery still uses the shared replication budget, so this removes the visibility-scan wait without guaranteeing a fixed delivery deadline. More collision-heavy motion can increase bandwidth and replication work; verify both alongside remote correction logs under load.

Remote client prediction uses a common server-tick timeline, anchored by the newest received player snapshot. An older snapshot is advanced by its tick age rather than being treated as current on arrival. This compensates for relative delivery delays without a fixed display buffer. Collision-constrained display checks remain budgeted at 3 ms per frame. Every two seconds the Unreal log reports `ClickNet remote` counters: accepted snapshots, maximum snapshot age in simulation milliseconds, maximum correction in meters, corrections exceeding 30 cm, maximum time between collision checks, and frames that exhausted the collision budget. Keep the game viewport focused when collecting these timings; background editor throttling increases check gaps.

## Bandwidth monitor

The server writes `bandwidth-live.json` beside the server project every 250 ms and appends `bandwidth-live.csv` once per second. The JSON snapshot lists connected players, their names, ping, recent inbound/outbound rates reported by GameNetworkingSockets, cumulative application payload bytes, `tickWorkMs`, the peak tick work time since the previous snapshot, and cumulative `lateTickCount`. Connection bandwidth queries are spread over about 15 loops so the snapshot does not query every client at once. The snapshot also reports `networkWorkMs`, `moverWorkMs`, `worldStepMs`, `replicationWorkMs`, and `statsWorkMs` from the last loop to locate server stalls. A sustained loop time above 16.7 ms or increasing late tick count means the 60 Hz target is under pressure; short overruns can be recovered by additional fixed physics steps. The CSV preserves traffic samples across server restarts. The server writes the JSON through a temporary file and atomic replacement, so a reader sees a complete snapshot. Pass `--stats E:\path\to\custom.json` to choose another location; the CSV uses the same base name.

Open `BandwidthMonitor\BandwidthMonitor.exe` to view the live player table and rolling traffic graph. The viewer looks for `bandwidth-live.json` in the server project directory by default; use **Browse file** if the server writes elsewhere. **History CSV** opens the saved samples.

The server assigns a fallback name such as `Player 1`. In Unreal, call `SetPlayerName` on `UClickNetSubsystem` before connecting, or launch the client with `-ClickNetPlayerName="Your Name"`. Names can also be changed while connected. The monitor shows the configured name after the client sends it.

Current limits: spawn is a server command-line setting shared by all joining players, and there is no remote-player Unreal actor spawning or interpolation layer. The server does not distribute maps or authenticate players. The client compares level hashes but the files must be copied/exported separately.
